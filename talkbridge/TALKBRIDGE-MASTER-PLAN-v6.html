Part 1 · Vision & intent

TalkBridge is a privacy-first WhatsApp-class experience for two people who don't share a language. One room = one partner = one language pair = one shared phrasebook. Chat, voice, and video are one continuous conversation on one transcript surface — typed messages and spoken words land in the same stream, every line shown side-by-side in both languages, each person always reading their own language on the left. No accounts, no servers holding content, no tracking. Installable as a PWA so calls ring and messages wait like a real messenger.

End product = shell experience (test.html) + bridge conversation engine (bridge-turn07-post-ship.html) + call presentation direction (2vid.html) + PWA layer (install, ring, message-waiting, mute-room), assembled by build-time injection into one file, deployed on GitHub Pages.

Design law — addition by subtraction. Fewer choices, fewer buttons, less friction. Elements must earn their place. No labels on auto-actions, no borders or badges without a job. Bridge look wins everywhere; one light theme everywhere.
Product laws (owner rulings, closed): app always boots to start screen · all rooms are one type, any room can call · chat surface is text-typed, voice lives in the call layer, both write to the one transcript · joiner sees only their room · bridge organs (transcript, compose, phrasebook) ship together, never split.

App installed as PWA. Incoming call = ringing notification with Accept / Decline actions; Accept opens the app straight into the call (S9), Decline sends a "missed call" pill into the transcript. Fingerprinting (mandatory every build)

  1. Manager locks the module fingerprint (SHA-256 of the exact block to inject) in the plan before the build.
  2. Doer injects, recomputes fingerprint from what actually landed in the output file.
  3. Mismatch = build auto-rejected, no debugging forward — rollback.
  4. Output file checksum recorded in the plan per attempt; deployed file byte-verified at the exact commit SHA (never at main).

Part 8 · Methodology

Doer / Manager protocol

  1. Owner (Confi) approves plan, rules on ambiguity, runs device gates. Sole decision-maker.
  2. Manager (Claude) owns this plan + graveyard: versions both, bumps every attempt, writes every doer prompt, reviews every doer report before any proceed. Pushes documents only — never code.
  3. Doer executes exactly one prompt, updates findings into the plan section named in the prompt, stops. Never self-extends scope.
  4. Failure order (mandatory): rollback deployed file → graveyard entry (version bump) → plan bump → only then a new build prompt. Never patch forward. Ever.

Turn-zero doer prompt (every prompt starts with this verbatim)

"Verify golden baseline checksums (Plan Part 5) before any work; mismatch = stop and report. Read only the plan sections named below. Execute only the numbered steps. Touch no file, surface, or behavior outside them — the do-not-touch registry (Part 9) is live. Report results into the plan section named. If anything is unclear or unexpected, stop and report; do not improvise, do not patch forward."

Gates & definition of done

  • Confidence 2.5/2.5 before build: spec read from plan (never memory) + fingerprint locked.
  • Pre-certification question, answered in the plan per piece: how do I know this will succeed — deterministic criteria only; lint is not done; device test is not an answer, it's the gift after certification.
  • Definition of done per piece: deployed + byte-verified at commit SHA + device-passed + plan updated + graveyard updated. Missing any one = not done.
  • Rollback map: every piece names its known-good file to restore (P1→golden floor; Pn→last passed piece's verified output, checksum recorded at its gate).
  • Change control: inventory (Part 3) and mockups (Part 2) are frozen. Any change = plan version bump with owner approval, before the change rides in any build.
  • After each confirmed ship: owner-provided process/self assessment → improvements enshrined here and in the graveyard, same turn.
  • Token discipline: no play-by-play; report started/completed/blocked only.

Part 9 · Registries

Do-not-touch (regression tripwires — retested at every device gate)

  • Boots to S1, panel closed, no room auto-open
  • Side-by-side bubble, viewer's language left, both languages always visible
  • One light theme everywhere; flag motif on ask screens only
  • One transcript: typed and spoken share it; call content permanent with 🎤 mark
  • Joiner room-locked; initiator rooms intact across updates (storage untouched)
  • Phrasebook shared per room; "Already saved" dedupe; Recently Deleted restore path
  • Go button always present; "/" search from compose everywhere including in-call

Open items (nothing hides)

  • S8 empty-card stacking defect — fix in P5
  • Receipt status-detail popup content — spec at P5 prompt time
  • PWA ring on iOS Safari limitations — validated in P6; fallback = in-app full-screen ring + badge
  • QR generation library choice — doer proposes at P3, manager approves (in-file, no CDN dependency)

Out of scope until post-ship

  • Language pair rollout beyond EN↔TH · PB search scale (1,500+ cards) · category-match dropdown redesign · O-Ring · TM

Graveyard learnings enshrined (high/low)

  • Runtime merge of two live apps = startup races, always. Build-time injection of a sealed, dormant module is the only survivor.
  • Shared namespace = silent function overwrites. One IIFE per module.
  • "It compiled / it lints" has shipped zero working builds. Only phone confirmation counts (§PIECE).
  • Patching forward converted 1-attempt problems into 10-attempt spirals. Rollback is cheaper every single time.
  • Splitting bridge organs across releases broke both halves. They move together.
  • Stale reads (raw CDN, main-ref, cached SHA) caused false passes and 409s. Contents API, exact commit SHA, fresh SHA before every write.
  • Building from memory instead of reading the spec produced the mockup failures of 2026-07-05. Inventory first, always.
