Part 1 · Vision & intent

TalkBridge is a privacy-first WhatsApp-class experience for two people who don't share a language. One room = one partner = one language pair = one shared phrasebook. Chat, voice, and video are one continuous conversation on one transcript surface — typed messages and spoken words land in the same stream, every line shown side-by-side in both languages, each person always reading their own language on the left. No accounts, no servers holding content, no tracking. Installable as a PWA so calls ring and messages wait like a real messenger.

End product = the planned TalkBridge app itself: one clean app state, one router, one room model, one message model, one phrasebook model, one call model, and one notification model, deployed as a PWA. Existing HTML artifacts are ingredient references only, not the pan, not the recipe, and not the finished layer.

Design law — addition by subtraction. Fewer choices, fewer buttons, less friction. Elements must earn their place. No labels on auto-actions, no borders or badges without a job. Bridge look wins everywhere; one light theme everywhere.
Product laws (owner rulings, closed): app always boots to start screen · all rooms are one type, any room can call · chat surface is text-typed, voice lives in the call layer, both write to the one transcript · joiner sees only their room · transcript, compose/search, and phrasebook are delivered as one working conversation product, not exposed as broken partial states.

Part 2 · UX walkthrough by role

MODE & CAPABILITY RULING — 2026-07-26 (owner-approved, supersedes all prior mute/toggle notes).
One room, one surface: the transcript. Phone and video are capabilities layered over the ongoing conversation, never separate screens.
Calls are real calls. Starting a call is a deliberate decision to transmit voice. The other party is notified with a ring, accepts or declines, and an unanswered call is recorded as a missed-call pill on the transcript. Hanging up de-escalates to chat in the same room; Exit (chat mode only) leaves the room to the start screen.
Sender — one switch. Mic ON: speech is transcribed and translated into bubbles always; raw voice is also transmitted whenever a call is live. Mic OFF (mute): nothing leaves — no transcription, no bubbles, no voice. Mute means mute. No partial-mute state exists.
Receiver — two binary toggles, in the room drawer (···): Ear = hear the other party's raw voice (default ON during a call); TTS = hear their translation read aloud (default OFF). Translation bubbles are always visible regardless. Each person controls only their own experience; the sender never controls what the receiver hears. Earlier incremental multi-step toggle behavior is dropped.
Top ribbon (never changes): ☰ · presence dot · room name — left; chat · phone · video mode icons — center, active teal, inactive grey; ··· — right.
Control strip (same background/height as ribbon, icons sized as mode icons): Chat = mic · exit(red). Phone = timer with green pulse left · mic · hang-up(red). Video = timer left · mic · camera · hang-up(red). Three controls align directly under the three mode icons; two controls sit at the midpoints. Non-red controls: no fill, inactive-grey. Red: filled red circle, white icon.
Composer: typing always available; keyboard voice-typing only when the strip mic is off (strip mic is master).
Transcript pills: call started · call ended with duration · missed call · "[Name] muted/unmuted".

## 3. What failed before

- **Shell-first bridge injection failed.** Injecting a sealed bridge into a shell base repeatedly woke the bridge at page load, broke shell functions, or silently ran stale dormant code.
- **Blind merge failed.** Combining two full apps produced namespace collisions and startup-order bugs that killed chat, search, and phrasebook.
- **Hidden prior-app / dormant-app approaches failed.** Contaminated dormant blocks in base files ran old code regardless of new fixes.
- **Negative-only gates failed.** Proving "the bug is gone" without proving "the capability works" shipped shells that did nothing.
- **Over-planning into many build stages failed.** Long stage ladders produced motion without a working app.
- **Fake prototype thinking failed.** Building toys to "prove" behavior that already works in real artifacts is waste.
- The actual missing piece is a **disciplined extraction/adaptation method**: know exactly what each artifact proves, lift exactly that, place it under single ownership, and verify positively with real clients.

### Stage 3: Test

Part 17 · Chrome strip — layout authority (2026-07-29)

This supersedes the strip and control-surface sections of the Mode & Capability spec. Where they conflict, this section wins. It is the build target for the strip in every mode.
THE MODEL

One strip. Three zones. The mic never moves.

There is exactly one row of chrome in every mode. It is divided into fixed zones, and only the contents of a zone change — never the zone itself. This is what makes the strip learnable: the outer edges hold still, and the middle tells you what you can do right now.

Left · identitywho you are with, and call status
Centre · broadcastwhat you are sending — fixed position
Right · lifecyclestart or end a call
···always present
Centre is what I am broadcasting. Right is call lifecycle. Mic and camera are my own state, so they sit centre. Phone, video-escalate and hang-up all change the call, so they sit right. Any new control belongs to whichever sentence it completes.
The mic is pinned to the true centre line of the strip — not centred as part of a group. The camera occupies a reserved slot to its right, empty in chat and phone. The mic therefore has one permanent address in all three modes and never shifts under the thumb as controls appear.
☰ and the red button are mutually exclusive. ☰ appears only in chat and means leave the room. Red appears only in a call and means end the call, stay in the room. Never both, never ambiguous — the strip announces its own context. Chat needs no exit icon: ☰ and the system back button already do that job.

Notes

MIC

The mic is a level meter

Transcription running whenever the mic is live is the central promise of the app. The mic icon therefore has to answer one question honestly and continuously: is my voice getting through right now? It answers it by filling from the bottom, clipped to the mic capsule.

silent
quiet
good level
loud
clipping
muted
no transcription
Logarithmic mapping, fast attack, slow release. Raw dB does not map to a pleasant 0–100; a log curve puts comfortable speech near half full instead of pinning or barely moving. The fill follows level up instantly and drifts down over roughly 200 ms — raw levels are jittery enough to strobe without it.
A meter that never moves is an unambiguous failure signal. Colour alone could not distinguish “on but silent” from “microphone broken”. An empty meter while you are speaking says permissions denied, wrong input device, or muted at the OS — instantly, without a diagnostic.
Amber fill = audio fine, transcription not landing. If Deepgram drops while capture continues, the meter keeps moving but the fill turns amber. Level and transcription health are two different facts and the meter carries both without a second icon. Silent failure of the core promise is the worst possible bug.

Off states

  • Mic off — slashed and red. Mute is total: no capture, no transcription, no transmission. The meter reads empty because there is genuinely nothing to show.
  • Camera off — same glyph, slashed and red. Still video mode; the band shows the avatar. Turning the camera back on is one tap, so the mode never collapses under the user.

MODULE 1 — AudioEngine (build this first, gate it alone before anything else)

Public interface — the ONLY functions any other code may call: 
AudioEngine.start(context)   // context = {surface:'chat'|'phone'|'video', room:RoomObject}
                              // Returns Promise<boolean>. Acquires mic if not already held,
                              // opens Deepgram socket(s), begins streaming. If status is
                              // already 'active' or 'starting', returns false immediately —
                              // NO surface may ever run two engines at once. This is enforced
                              // HERE, not by callers remembering to check.

AudioEngine.stop()           // Tears down everything: closes sockets, stops all tracks,
                              // releases the stream, resets status to 'idle'. Idempotent —
                              // calling stop() when already idle is a safe no-op.

AudioEngine.isActive()       // Returns boolean. The ONLY way any surface checks mic state.

AudioEngine.currentSurface() // Returns 'chat'|'phone'|'video'|null. Used by the chrome strip
                              // (Module 3) to know what to render — it must never infer this
                              // from its own local state.

AudioEngine.on(eventName, fn) // Subscribe. Events: 'transcript-final' fires with
                              // {text, sourceLang, surface}. 'transcript-interim' fires with
                              // {text}. 'error' fires with {code, message} — codes are:
                              // 'no-key' | 'mic-denied' | 'no-stream' | 'socket-error'.
                              // 'status-change' fires with {status}.
Internal behaviour contract (what the module does, not how — implementer's choice on mechanics, using the extracted bridge-turn08-base.html pipeline as the proven reference for the WebSocket/AudioWorklet mechanics):
  • start() acquires exactly one getUserMedia({audio:...}) stream. If surface==='video', video is requested by the CALLER separately (video track is NOT this module's concern — camera is Module 2's problem, this module only ever touches audio tracks).
