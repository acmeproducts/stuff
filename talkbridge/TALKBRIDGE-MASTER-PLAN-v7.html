RELEASE 1 — Strip States + Chat Mic

Owner: the single chrome row and its CSS state machine, plus one new chat-mode mic button wired to the existing Deepgram pipeline.

What the baseline has: a ribbon and a separate call-ctl bar below it. The call-ctl bar is deleted entirely. The ribbon becomes one row that transforms across three states via CSS class.

Three states, confirmed anatomy:

Chat mic behavior: reuses the existing Deepgram call pipeline — no new module. Spoken text routes into the same bubble path typed text uses. Mic state (on/off) is stored before any call escalation and restored exactly on hang-up. If chat mic is on when a call starts, it auto-stops for the duration of the call; on hang-up it resumes. If it was off, it stays off after hang-up.

Mute rule (unchanged from Mode ruling): mic off = total mute — no transcription, no transmission, no bubbles. No partial state.

MIC ICON — not a static glyph, a live level meter. Full spec: Part 17 “MIC” card, below the appendix banner (reference only, but binding for behavior). Summary, so this isn't missed by only reading current-plan text:
  • The mic capsule fills from the bottom with teal, clipped to the capsule shape, tracking live input level.
  • Log-scale mapping, not raw dB — comfortable speech sits near half full, not pinned to one extreme.
  • Fast attack, ~200ms release — the fill rises instantly and drifts back down, rather than jittering with every raw sample.
  • An empty meter while actively speaking is itself the failure signal for a broken mic or denied permission — no separate error icon needed.
  • Amber fill, not teal, means audio is fine but transcription isn't landing — e.g. Deepgram dropped mid-call while capture continues. Level and transcription health are two different facts carried by the same meter, no second icon.
  • Off state: slashed, red — not just dimmed.
Camera icon uses the same slash-for-off convention, red when off.

Credential handling — ALL credentials, one pass (2026-07-30, owner-directed): the Deepgram key, GitHub PAT, and TURN token all live on one screen (Calling & sync keys), so all three are live-verified on save together here, not split across releases. Modeled on bridge-turn08-pre-base.html's existing working verify-on-save pattern. Every connection failure, for every credential, is logged to the debug log (failure-only — no per-success noise). The GitHub PAT rejection toast's on-screen duration is increased — it currently disappears before it can be read.

Escalation/de-escalation: tapping the call or video icon escalates from chat state to the appropriate call state. Hang-up de-escalates back to chat state. Strip returns to its exact pre-call layout, no exceptions.

GAP CONFIRMED, SOLVED (2026-07-30, owner-directed): the confirmed three-state anatomy has no control for leaving a room back to the start screen. Two earlier drafts of this finding were wrong and are retracted: (1) the claim that the drawer's Close button is hard to find was wrong — the drawer already has a separate, pinned X in its own header that closes it instantly with no scrolling required; (2) the suggestion to repurpose ☰ for this was wrong — ☰ opens the room-switcher panel, full stop, and must not be given a second meaning.

Final solution: the room-switcher panel (opened by ☰) gets a standing first entry, above every room card — an application info card, not tied to any specific room. Tapping it shows the app's true start/splash screen. Tapping that splash screen's background closes the panel, returning cleanly to the true start state with no room active.

This exact concept — leaving a room to a splash screen — already existed once before, confirmed by direct inspection of talkbridge-app-a7r4.html (graveyarded, reference only): it had a working function that cleared the active room and returned to the start screen. That file wired it to a dedicated exit button in the old two-strip control design, which no longer exists under the current single-row anatomy. The underlying "clear room, show start screen" logic is reusable; only its trigger changes — from a strip button to the new first-position info card in the panel described above.

SCOPE RULING (2026-07-30, owner-confirmed): the phrasebook is TWO separate books per language pair — one per direction. EN→TH and TH→EN are different files, never merged. This matches existing code behavior exactly and is now the binding rule. Any language elsewhere in this document describing a single shared pair-scoped book is superseded and incorrect — ignore it.
GAP FOUND (2026-07-30): today’s direction-loading confusion traces to how the correct book gets picked. It currently depends on whether a person created the room or joined it — a value set once, permanently, at the moment the room was made, and never revisited. That is exactly why a room can silently show as "joined" even to its own owner, and pull the wrong-seeming book. Recommendation: pick the book from the room’s own fixed, stored language pair instead of from creator/joiner status. Same two-book rule, no longer dependent on a value that can quietly drift.
SUPERSEDED (2026-07-30) — see version-management ruling directly below. The original defect was that using a phrase bumped the shared version number for no real change. The fix is no longer "stop usage from counting as dirty" — it's "stop bridge from managing version numbers at all." See below.
VERSION-MANAGEMENT RULING (2026-07-30, owner-confirmed): bridge, as the running app, has no business managing phrasebook filenames or version numbers. On any change — content edit OR routine usage — bridge simply overwrites the file it already has loaded, at the version number it already has loaded. It never invents a new, higher version number itself. A new version only ever comes from a separate, external phrasebook release process (outside the app). On every pull (room entry, reconnect, reload), bridge always selects whichever file has the highest version number present in the repository — so if that external process publishes a bump, the next person to enter the room picks it up automatically, with no bridge-side version logic required. This also resolves the usage-dirty concern above directly: since saving no longer bumps a version number, there's no harm in also capturing usage counts on save — do so freely, on every change, without needing to distinguish "real" edits from "just usage."
KNOWN DEFECT, data-loss risk, folds into Release 3: every successful phrasebook pull (room entry, reconnect, reload) unconditionally replaces local cards with whatever is on GitHub and clears any pending local changes, with no warning. Recommendation: a pull must never discard unwritten local changes — write them back first, then pull. A dirty local copy blocks or defers a pull until its own write-back completes.

ADDENDUM — Credential & Error Trap Audit (2026-07-30)

Direct inspection of bridge-turn08-ship.html found that credential failures are inconsistently surfaced to the user. Some are toasted clearly; others fail completely silently, with the only trace being a debug-log entry a normal user would never check. This is the leading explanation for "works on desktop, fails silently on mobile" — each device stores its own copy of each credential, so a bad paste or truncated value on one device with no error path produces exactly this symptom.

CredentialMissingInvalid / rejected by serverWhat the user currently sees on invalid
Deepgram key (speech)Toasted: "Deepgram key missing"Connection refused, silently retried every 2 seconds for the whole callNothing. No toast, no indicator. Call proceeds with total silence where transcription should be.
Cloudflare TURN tokenNot confirmed by inspectionNot confirmed by inspectionNot confirmed — likely produces degraded/failed video connection with no explanation
GitHub PAT (phrasebook sync)Toasted: "add GitHub PAT in Calling & sync keys"Toasted distinctly: "GitHub rejected the PAT"Correctly surfaced — this one already works as it should

Recommendations (owner-directed, 2026-07-30):

  • Every credential failure — missing or invalid — must produce a visible, specific toast naming which credential and which failure state. GitHub PAT already does this correctly; match that standard everywhere. The existing GitHub PAT toast itself needs a fix too — it was observed disappearing too quickly to be read, useful only for noticing something failed, not what to do about it. Toasts for credential failures need enough on-screen time to actually be read.
  • An invalid Deepgram key must stop silently retrying after a small, fixed number of attempts and surface a persistent, dismissable state — not a toast that can be missed — so a call never runs indefinitely with dead transcription and no visible sign.
  • The Calling & sync keys screen must test each credential live on save and show a pass/fail indicator per key, catching bad credentials before they cause a silent mid-call failure. A working model for this already exists in bridge-turn08-pre-base.html — it opens a real test connection as a key is typed (and again on app load for a saved key) and shows a live "Verifying…" status that resolves to pass or fail. Build to that existing pattern rather than inventing a new one.
  • Debug log requirement: every credential failure, for every credential, must be logged — this is what makes an intermittent failure diagnosable after the fact instead of only visible in the moment. Part 1 · Vision & intent

TalkBridge is a privacy-first WhatsApp-class experience for two people who don't share a language. One room = one partner = one language pair = one shared phrasebook. Chat, voice, and video are one continuous conversation on one transcript surface — typed messages and spoken words land in the same stream, every line shown side-by-side in both languages, each person always reading their own language on the left. No accounts, no servers holding content, no tracking. Installable as a PWA so calls ring and messages wait like a real messenger.

End product = the planned TalkBridge app itself: one clean app state, one router, one room model, one message model, one phrasebook model, one call model, and one notification model, deployed as a PWA. Existing HTML artifacts are ingredient references only, not the pan, not the recipe, and not the finished layer.

Design law — addition by subtraction. Fewer choices, fewer buttons, less friction. Elements must earn their place. No labels on auto-actions, no borders or badges without a job. Bridge look wins everywhere; one light theme everywhere.
Product laws (owner rulings, closed): app always boots to start screen · all rooms are one type, any room can call · chat surface is text-typed, voice lives in the call layer, both write to the one transcript · joiner sees only their room · transcript, compose/search, and phrasebook are delivered as one working conversation product, not exposed as broken partial states.

Gates & definition of done

  • Confidence 2.5/2.5 before build: spec read from plan (never memory) + target layer/action map understood.
  • Pre-certification question, answered in the plan per layer: how do I know this will work — deterministic criteria plus the named positive user capability; lint is not done.
  • Definition of done per layer: deployed + byte-verified at commit SHA + positive device path passed + plan updated + graveyard updated. Missing any one = not done.
  • Rollback map: every layer names its known-good app target or prior committed plan package to restore, with checksum recorded at its gate.
  • Change control: inventory (Part 3) and mockups (Part 2) are frozen. Any change = plan version bump with owner approval, before the change rides in any build.
  • After each confirmed ship: owner-provided process/self assessment → improvements enshrined here and in the graveyard, same turn.
  • Token discipline: no play-by-play; report started/completed/blocked only.

Implementation staging vs product shipping

The real app may be built in layers, but exposed states must be coherent final-product states. No final/pilot build may expose transcript without compose/search/phrasebook, or compose/search/phrasebook without transcript. Temporary scaffolding is allowed only in the planning/package layer or when clearly inaccessible to users.

Mandatory stop conditions

  • Stop if cold boot shows any room/call surface, any prior-app surface, or any permission prompt before user intent.
  • Stop if a prior fixed issue reappears, a touched surface passes but an adjacent surface breaks, or deployed bytes do not match verified checksum.
  • Stop if the positive bilingual messaging path fails after L2, or if a second patch is proposed for the same failed gate without rollback/re-plan.

Part 17 · Chrome strip — layout authority (2026-07-29)

This supersedes the strip and control-surface sections of the Mode & Capability spec. Where they conflict, this section wins. It is the build target for the strip in every mode.
THE MODEL

One strip. Three zones. The mic never moves.

There is exactly one row of chrome in every mode. It is divided into fixed zones, and only the contents of a zone change — never the zone itself. This is what makes the strip learnable: the outer edges hold still, and the middle tells you what you can do right now.

Left · identitywho you are with, and call status
Centre · broadcastwhat you are sending — fixed position
Right · lifecyclestart or end a call
···always present
Centre is what I am broadcasting. Right is call lifecycle. Mic and camera are my own state, so they sit centre. Phone, video-escalate and hang-up all change the call, so they sit right. Any new control belongs to whichever sentence it completes.
The mic is pinned to the true centre line of the strip — not centred as part of a group. The camera occupies a reserved slot to its right, empty in chat and phone. The mic therefore has one permanent address in all three modes and never shifts under the thumb as controls appear.
☰ and the red button are mutually exclusive. ☰ appears only in chat and means leave the room. Red appears only in a call and means end the call, stay in the room. Never both, never ambiguous — the strip announces its own context. Chat needs no exit icon: ☰ and the system back button already do that job.

Notes

MIC

The mic is a level meter

Transcription running whenever the mic is live is the central promise of the app. The mic icon therefore has to answer one question honestly and continuously: is my voice getting through right now? It answers it by filling from the bottom, clipped to the mic capsule.

muted

Logarithmic mapping, fast attack, slow release. Raw dB does not map to a pleasant 0–100; a log curve puts comfortable speech near half full instead of pinning or barely moving. The fill follows level up instantly and drifts down over roughly 200 ms — raw levels are jittery enough to strobe without it.
A meter that never moves is an unambiguous failure signal. Colour alone could not distinguish “on but silent” from “microphone broken”. An empty meter while you are speaking says permissions denied, wrong input device, or muted at the OS — instantly, without a diagnostic.
Amber fill = audio fine, transcription not landing. If Deepgram drops while capture continues, the meter keeps moving but the fill turns amber. Level and transcription health are two different facts and the meter carries both without a second icon. Silent failure of the core promise is the worst possible bug.

Off states

  • Mic off — slashed and red. Mute is total: no capture, no transcription, no transmission. The meter reads empty because there is genuinely nothing to show.
  • Camera off — same glyph, slashed and red. Still video mode; the band shows the avatar. Turning the camera back on is one tap, so the mode never collapses under the user.
