# GY-009 — Poll-driven completed-state rerender, ambiguous stale-plan presentation, and non-operable selector panes

**Status:** REJECTED
**Evidence:** Turn 01 Base-22 owner test
**Decision date:** 2026-08-30

## Rejected approach

Do not continuously rerender a completed Index surface through the same loading path used for active work. Do not show stale/historical plan rows as though they are the current plan while a current-plan generation request fails with only a transient toast. Do not implement a three-panel selector whose center/selected panes cannot independently scroll, whose Available list lacks local search, or whose commit action is buried inside the Selected pane.

## Why rejected

Base-22 owner testing showed that the Index surface visibly flashes after completion because periodic refresh invokes the full render path. The Plan surface simultaneously displayed `State: stale` rows and returned `no current evidence is available`, which gives neither a coherent state model nor a recovery action. The canonical selector also failed basic long-list ergonomics.

## Required replacement

1. Poll/rerender Index only while an index job is active; completed state is stable until an explicit state-changing action.
2. Plan surface must distinguish Current Plan from Previous/Stale Plan. Failed generation must render a persistent explanation and direct recovery action, not only a toast.
3. If current fingerprint evidence is absent/stale, the UI must say so and offer Re-index; it must not imply that displayed stale rows are executable.
4. A successful Generate Plan must render the resulting draft immediately in the Plan surface and label it clearly as the current executable plan.
5. Available Folders and Selected panes must independently scroll.
6. Available Folders must have an in-memory search/filter control that does not re-enumerate storage.
7. The selector commit action must live in the outer modal footer adjacent to Cancel for every role.

Base-22 remains rejected owner-gate evidence only.
