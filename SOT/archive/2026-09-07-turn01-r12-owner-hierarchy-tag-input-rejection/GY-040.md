# GY-040 — R12 owner rejection: flat SSOT listing and destructive tag-input refresh

Date: 2026-09-07

R12 mechanically qualified and successfully migrated the live SSOT to schema 6, but the owner rejected the Profile UX.

Observed defects:

- Typing into the tag field loses focus / hides the mobile keyboard before the user can press Enter. Periodic redraw/polling is allowed to reconstruct the active tag editor.
- Tag removal is presented as a separate bulk remove control even though the accepted interaction is assigned tag = chip with `×`; the chip `×` is the removal control.
- The Profile surface renders the SSOT virtual volume as a flat list of folders/files rather than a navigable storage hierarchy.
- There is no master-detail relationship between folder navigation and the contents/details of the selected folder/file.
- The resulting surface is an undifferentiated mass of SSOT rows and does not behave like a virtual storage volume.

Required correction for R13:

1. R12 remains the mechanically qualified backend/schema baseline. Do not patch the installed/generated R12 HTML.
2. R13 is a clean UI source advance composed from the pinned R9 → R10 → R11 → R12 source integrators, followed once by an R13 UI integrator.
3. Profile must be a master-detail virtual-volume browser:
   - master = hierarchical expandable folder tree;
   - detail = selected folder's immediate subfolders/files, or selected file metadata;
   - Omnisearch filters the virtual volume while retaining folder ancestry/context.
4. Tag entry must use a persistent inline editor with type-ahead pool matches and Enter-to-assign. Polling/data refresh must not redraw the active editor or dismiss the keyboard.
5. Assigned/effective tags render as chips. Removal is via the chip `×` only. For inherited tags, the chip identifies inheritance and `×` removes the governing folder assignment, not an unrelated direct descendant assignment.
6. Bulk tag assignment remains available for a stable selected result set. Bulk removal is exposed through removable common/effective tag chips, not a separate generic Remove Tag button.
7. Selection, expanded folders, selected node, Omnisearch, tag input/focus, scroll, and disclosure state survive refresh.
8. No backend/schema change is required unless a concrete R13 UI requirement cannot be satisfied from the qualified R12 Profile API.
