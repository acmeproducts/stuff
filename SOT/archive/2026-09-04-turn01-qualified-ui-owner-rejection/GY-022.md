# GY-022 — mechanically qualified Base UI rejected by owner

Date: 2026-09-04

## Status

REJECTED PRODUCT SURFACE. Retain backend/runtime qualification evidence only.

## What passed

The SOT backend and coordination foundation passed the executable gates previously recorded in the Turn 01 Base plan, including cross-project concurrency, same-project mutation exclusion, durable evidence and plans, stale-generation protection, pause/stop/restart durability, activity reconstruction, real polling UI reconciliation, installer qualification, live host cutover, health/schema checks, and public byte identity.

## Owner rejection

After successful live qualification, the owner rejected the product architecture because each project still required separate project/step navigation and context changes. The intended product is one continuous project surface where the lifecycle is visible and operable in one flow:

`Scope / Storage → Index → Review → Plan → Execute → Activity`

The rejected patterns include buried review navigation, duplicated project-vs-step navigation, inert/context-switching tabs, hidden controls, and UI refresh behavior that can compete with operator state.

## Permanent rule

Do not patch the rejected UI surface forward. Preserve only its qualified backend/runtime foundation and accepted functional contracts. Any replacement UI must be a clean single-project-surface implementation and must mechanically prove that real polling/progress reconciliation preserves the active project, search text, open picker/modal, focused input/edit value, expanded sections, and scroll position.
