# GY-019 — Unserialized project mutation and destructive polling refresh

**Status:** REJECTED
**Evidence:** 2026-09-02 owner test of latest SOT release
**Decision date:** 2026-09-02

## Rejected approach

Allow index, re-index, planning, execution, scheduler recovery, and UI polling/refresh to independently infer and mutate project state without one authoritative per-project coordinator, durable operation generation, or stale-result rejection.

Also rejected: treating "multi-threaded" as permission for multiple state-mutating operations against the same project to run concurrently, and allowing background refresh to replace interactive UI state while the operator is selecting/navigating.

## Why it is rejected

Owner testing exposed a coordination failure rather than a single Plan-screen defect:

- indexed files were rediscovered but did not remain durably plan-eligible;
- displayed evidence revision and plan-validation state contradicted each other;
- re-index could race existing evidence/job state;
- UI refresh fought selection/navigation;
- there was insufficient durable job/event history to identify which operation changed or invalidated project state.

The existing backend already spawns worker processes, so the missing property is not threading itself. The missing property is controlled concurrency and authoritative lifecycle ownership.

## Do not repeat

Do not:

- run more than one state-mutating operation concurrently for the same project;
- let a stale worker completion overwrite a newer project/evidence generation;
- derive lifecycle state independently in multiple UI/backend paths;
- reset operator selection, modal, tab, scroll, or navigation state during polling;
- make UI responsiveness depend on index/hash/plan/execute completion;
- use in-memory worker maps as the only explanation of what happened;
- patch the rejected owner-tested runtime forward as a new ancestor.

## Required replacement

1. Preserve real concurrency across different projects and inside bounded worker pools.
2. Serialize lifecycle mutation per project through one coordinator/lease.
3. Use explicit lifecycle states: `idle -> indexing -> indexed -> planning -> planned -> executing`, plus `paused`, `failed`, and `cancelled`.
4. Give every mutating operation a durable operation/job ID and project generation; commit results only when the generation still matches.
5. Make evidence revision advance atomically only after a complete successful index commit; failed/cancelled/stale index work must not replace current evidence.
6. Bind plans to an exact committed evidence revision and reject stale plans deterministically.
7. Make polling/event refresh patch data only; never replace active operator interaction state.
8. Persist lifecycle/job/event transitions with timestamps, operation IDs, project token, prior/new state, evidence revision, and failure/cancellation reason.
9. Expose enough activity history to diagnose a project without reconstructing behavior from the UI.

## Recovery anchor

Return to the governed clean SOT lineage declared in `SOT-TURN01-BASE-PLAN.md`. Preserve the failed release only as evidence. Rebuild the coordination delta from the clean lineage and mechanically qualify concurrency/state-transition invariants before owner handoff.
