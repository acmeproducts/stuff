# GY-021 — UI/backend coupling, destructive refresh churn, and non-authoritative indexed presentation

**Status:** REJECTED  
**Decision date:** 2026-09-03  
**Rejected build:** `2026.09.03.sot-turn01-coordination-2`

## Owner result

The release is rejected in browser testing.

Observed behavior:

- startup is slow enough to appear frozen;
- project navigation and project actions are sluggish;
- loading Index does not leave a stable visibly indexed project;
- the operator is pushed back toward re-indexing before forward workflow can continue;
- re-index can sit without useful visible progress;
- the UI repeatedly flashes during background activity;
- interaction feels bound to background work rather than independent from it;
- the system is therefore unusable for completing one project and cannot satisfy the multi-project/parallel contract.

## Root architectural failure

The release still treats backend hydration and periodic reconciliation as part of rendering the interactive surface. The browser waits on compound backend reads during startup and rebuilds substantial DOM state when polling reports changes. Project presentation also gives latest processing-run state too much authority over the durable committed evidence state. An interrupted/replacement run can therefore visually demote a project that still has valid committed evidence.

This violates the central contract: UI interaction must be immediate and independent of filesystem/index/plan/execution work. Background work may update activity/progress, but it may not own navigation, tab rendering, selection, or the existence of previously committed evidence.

## Rejected approach

Do not:

- gate initial shell/project navigation on `Promise.all` hydration of projects, health, rollup, scheduler, or expensive aggregate queries;
- rebuild project cards/workspace/index content on a timer merely because backend counters changed;
- use latest `processing_state` as the primary project workflow/index truth when a committed `evidence_revision` exists;
- blank a stable Index surface while waiting for status/progress reads;
- use polling rerender as a substitute for an explicit activity/progress surface;
- allow replacement-index lifecycle state to make committed evidence appear absent;
- hand off another candidate whose responsiveness is only inferred from DOM-state marker tests.

## Required replacement

The next candidate must implement a hard UI/work separation:

1. **Immediate shell:** render app chrome, cached project summaries, selected project and selected tab synchronously before any network request completes.
2. **Independent hydration:** project list, health, rollup, scheduler and activity hydrate independently; failure or slowness in one cannot block the others.
3. **Durable project truth:** committed evidence/plan state is displayed from authoritative revision fields. Active/replacement work is a separate operation overlay, never a replacement for committed state.
4. **No polling rerender:** background refresh mutates only named status/progress/activity DOM nodes. It never calls full card/workspace/Index render functions.
5. **Instant navigation:** selecting a project/tab changes the visible surface synchronously. Data panels may show a contained loading/progress state inside the already-visible surface.
6. **Persistent Index:** if evidence revision N is committed, Index remains available and plan-eligible through refresh, navigation, restart, and replacement indexing until N+1 successfully commits.
7. **Visible activity:** every long operation displays state, phase, counts, bytes, current item, elapsed activity and pause/stop affordances without making the rest of the UI wait.
8. **Responsiveness qualification:** automated browser/DOM qualification must inject deliberately slow backend responses and continuous progress changes while asserting that navigation/tab actions complete immediately and no full-surface rerender occurs.

## Lineage consequence

`2026.09.03.sot-turn01-coordination-2` is rejected evidence only. It must not become the implementation ancestor. Recovery continues from the governed accepted pre-base/Base integration lineage, reapplying only coordination behavior that passes the stricter decoupling and durability gates above.
