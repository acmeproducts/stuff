# GY-017 — Windows browser harness used a WSL-backed profile

## Rejected approach

Launching Windows Edge/Chrome from WSL while placing `--user-data-dir` under WSL `/tmp` and converting that path with `wslpath -w`.

## Failure mode

Windows browser support processes such as Crashpad require Windows-native filesystem locking/pipe semantics. A WSL/UNC-backed profile can fail before page execution, yielding browser-process errors and a missing application boot sentinel. This makes the release harness incapable of distinguishing application failure from harness failure.

## Permanent rule

When a Windows `.exe` browser is used from WSL:

- browser profile directories MUST be created in Windows-native `%TEMP%` (or another Windows-native local filesystem path);
- profile cleanup MUST be performed with Windows-native tools;
- the browser harness MUST prove liveness with a deterministic self-test before application boot evidence is accepted;
- a harness failure blocks qualification and may never be waived as owner testing.

Linux-native browsers may continue to use Linux-native temporary profile directories.

Executable parser gates remain necessary but are not sufficient; browser execution evidence is only valid after the harness itself has passed its self-test.
