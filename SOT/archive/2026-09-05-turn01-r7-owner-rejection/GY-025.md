# GY-025 — R7 presents contradictory implementation state instead of storage truth

Date: 2026-09-05
Status: OWNER REJECTED

## Owner evidence

Owner screenshots of the live R7 installation show that the interface cannot answer the basic question: **what is my storage situation and what do I do next?**

Examples visible in the live UI:

- `fulltime` is labeled **Protected** and the SSOT counts it protected, while the same project shows Index operation `error`, Plan `stale`, and `Verify Result` as the next action.
- `try` is labeled **Protected** with `0 B · 0 files`, committed evidence `r10`, Plan `none`, and `Protect Files` disabled. An empty project cannot be evidence that storage is protected.
- `test` and `the c gate` are labeled **Ready to Protect**, but the UI does not show how much data is already safely present, how much is missing from Target, how much is missing from Backup, or what protection will actually copy before asking the operator to press Protect.
- SSOT says **No immediate attention required** even though one visible project has an index error/stale plan and another has zero indexed files/no plan.
- The six-stage lifecycle and numerous implementation controls expose internal machinery (`closed`, `Continue`, `Pause`, `Stop`, stale/current revisions) without converting it into an estate-level storage reconciliation.
- The left rail duplicates action buttons but still does not communicate storage coverage.

## Why this is rejected

SOT's purpose is storage reconciliation, not workflow-state visualization. A project cannot be classified from isolated flags such as zero `target_missing_content` or zero `backup_missing_content` when there is no meaningful committed content. `0 missing` with `0 content` is **not protected**.

The UI currently asks the operator to understand evidence revisions, plan freshness, worker state, and lifecycle controls before it tells them the actual storage facts. That reverses the product hierarchy.

## Replacement contract

The next release must be a clean source redesign, not a patch-forward of R7 presentation logic.

### SSOT first

The first screen must answer, in storage terms:

1. **Source** — how much material SOT is responsible for across projects.
2. **Safe copies** — how much of that material is confirmed on Target and Backup.
3. **Unprotected** — how much source material is missing one or both required copies.
4. **Unknown / needs scan** — projects whose evidence is empty, stale, failed, or insufficient to make a protection claim.
5. **Next actions** — a short ordered list of concrete corrections with one direct button each.

Never count an empty/unknown project as Protected merely because missing-copy counters are zero.

### Project first question: coverage

Each project surface must lead with a visual storage reconciliation:

`SOURCE → TARGET → BACKUP`

For each leg show meaningful bytes/files known, present, missing, and unknown. Then state one plain-language condition, for example:

- `114 files / 1.6 TB indexed; 12 files still need a Target copy` → **Protect 12 files**
- `9,865 files indexed; Target status unknown because the last index failed` → **Finish index**
- `0 files indexed` → **Nothing has been indexed yet** → **Index now**
- `Target not defined` → **Choose Target**
- `Backup not defined` → **Choose Backup**
- all required copies confirmed → **Storage protected**

### Workflow is secondary

Setup/Index/Review/Plan/Protect/Verify may remain available as advanced detail, but must not be the primary explanation of storage state. Hide invalid controls; do not offer Pause/Stop/Continue when no matching live operation exists. Do not surface `closed` as an operator status.

### Truth rules

A `Protected` classification requires positive committed evidence plus confirmed copy coverage for that exact evidence revision. Empty evidence, stale evidence, failed current scan, stale/missing plan, or unknown destination coverage must be represented as unknown/incomplete rather than healthy.

SSOT aggregation must use the same truth resolver as each project so the overview can never claim `No immediate attention required` while a constituent project is visibly unresolved.
