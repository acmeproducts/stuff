# GY-023 — Non-actionable machine status, refresh-owned disclosure state, and project-only SOT framing

**Status:** REJECTED  
**Decision date:** 2026-09-05  
**Evidence:** owner test of Turn 01 Base R5 `SOT-turn01-base-r5-simple-protect`

## Rejected approach

1. Render transient backend labels such as `Error` as the primary project status.
2. Show a raw failure and require the operator to infer the corrective action.
3. Re-render project details on polling in a way that closes sections the operator opened.
4. Present project-local SOT surfaces without an installation-wide SSOT reconciliation layer.
5. Hide lifecycle truth behind a protection wizard instead of visibly showing completed/current/next stages.

## Why rejected

The storage problem is bounded and deterministic: Sources are inventoried and indexed, findings become committed evidence, safe-copy destinations are configured, a plan is produced, protection is executed, and the result is verified. The UI should therefore be able to translate nearly every incomplete/error condition into a specific missing requirement or failed operation plus its direct repair action.

A project with valid committed evidence is not simply `Error` because a later Target operation failed. Durable progress and transient operation state must be shown separately.

Polling is server-owned reconciliation, not navigation. It may update progress and facts but may not close an operator-opened section or reset other operator state.

Project SOTs also require a top-level SSOT view that reconciles all projects and tells the operator what is protected, what is ready, what needs attention, and the next corrective action for each item.

## Do not repeat

- Do not use `Error` as the primary operator-facing project state when a more specific condition is known.
- Do not surface a correctable problem without a corrective control beside it.
- Do not make diagnostics the normal path to discover what to do next.
- Do not let polling reconstruct `<details>` expansion, selection, scroll, focus, picker, modal, or search state.
- Do not conflate committed lifecycle state with transient operation state.
- Do not treat the set of independent project cards as the installation-wide SSOT management layer.

## Required replacement

R6 must be a clean UI build against the qualified backend contract and must provide:

1. **SSOT overview:** aggregate project/storage truth and attention queue across all projects.
2. **Visual project lifecycle:** `Setup → Index → Review → Plan → Protect → Verify`, with completed/current/pending visually distinct.
3. **Explicit next action:** every project exposes one plain-language next requirement/action.
4. **Actionable conditions:** e.g. `Needs Target` + `Choose Target`, `Index incomplete` + `Continue Index`, `Plan stale` + `Update Plan`.
5. **Durable + transient separation:** e.g. `Indexed r4 · Re-indexing 61%`; a failed replacement operation cannot erase `Indexed r4`.
6. **Operator-owned disclosure:** opened sections stay open until the operator closes them or selects another project.
7. **Diagnostics secondary:** raw exceptions, paths, operation IDs and event payloads remain available but do not replace the actionable explanation.
