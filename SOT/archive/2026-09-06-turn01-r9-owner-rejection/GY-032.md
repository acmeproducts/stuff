# GY-032 — R9 database-centered shell without operating product

Date: 2026-09-06
Stage: Turn 01 Base
Rejected release: R9 database-centered master/detail

## Owner-observed failure

R9 materially improved the dashboard hierarchy but removed or hid essential SOT operating capability. The owner could not assign project Sources, define Target/Backup destinations, configure AI, understand duplicate groups, understand where duplicate bytes physically exist, distinguish shared content from redundant source copies, receive concrete storage recommendations, or see meaningful indexing telemetry beyond a queued/running label.

The result was a dashboard/reporting shell rather than a storage-management product.

## Required correction

The next release must preserve the accepted R9 dashboard/master-detail/database architecture while restoring the product behind it:

1. Project detail exposes Source, Target/Copy A, and Backup/Copy B configuration using the live volume/folder picker and destination-folder creation.
2. Settings exposes AI provider, model, and browser-local key configuration.
3. SSOT produces deterministic storage intelligence from fingerprints: duplicate groups, physical locations, redundant source bytes, cross-project shared content, missing verified protection, and prioritized recommendations.
4. Dashboard and project detail explain what SOT found and what action follows; Deep Dive/Database remain evidence inspection rather than the only source of meaning.
5. Active indexing must expose real durable counters/current work when the backend has them; queued state must not masquerade as useful progress.

## Lineage rule

R9 is owner-rejected as a product release but its mechanically qualified R9 source is the governed baseline for R10 because the owner explicitly accepted the dashboard as "definitely better" and requested restoration of missing capability into it. R10 is one clean source diff against that qualified R9 baseline. Failed generated artifacts remain evidence only.
