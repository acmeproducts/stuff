# GY-021 — False-positive UI reconciliation qualification + installer handoff assertion mismatch

**Status:** REJECTED QUALIFICATION / HANDOFF EVIDENCE  
**Decision date:** 2026-09-04  
**Repository head observed immediately before this archive:** `b36af59159cedb6c92cb0833a5204db0899ed395`

## What happened

The repository qualification run `33919314140` reported gates 1–10 green. The subsequent canonical installer handoff, pinned at `a6b5f68b3a22f78db8508c3de5794c9327034452/install-SOT-turn01-base.sh`, failed before cutover while validating the generated UI:

```text
AssertionError: function backgroundPulse()
```

The host archive for that failed handoff is:

`/home/support/.openclaw/workspace/https/report/SOT/archive/20260904-144223-turn01-base-qualified-release`

The installer exited `1`. It failed before cutover, so the live runtime remained healthy on build `2026.09.03.sot-turn01-coordination-2`, schema `5`, and the public page continued returning HTTP 200.

## Root cause

The gate-9 Chromium harness contained:

```js
if(typeof backgroundPulse==='function') await backgroundPulse();
```

The exact clean-lineage generated UI does not define `backgroundPulse`. Therefore the expression silently skipped the intended progress refresh and the harness still reported PASS. That made gate 9 a false positive: it checked operator-state invariants without proving that an actual polling/progress update occurred.

Separately, the installer asserted that the generated UI contained the nonexistent literal `function backgroundPulse()`. The installer qualification workflow only checked shell syntax, source pins, and URL resolvability; it did not reproduce the installer's candidate-generation assertions, so it failed to catch the mismatch before owner handoff.

## Rejected approach

- A browser reconciliation test that conditionally skips the refresh mechanism when that mechanism is absent.
- Treating `typeof X === 'function'` as sufficient evidence that a real progress update occurred.
- Installer qualification that does not generate and validate the same candidate the installer will validate before cutover.
- Asking the owner to rerun an installer after this class of mismatch without first repairing and requalifying the repository-side handoff path.

## Required correction

1. Gate 9 must drive the exact generated UI through its real 3-second `/projects` + `/rollup` polling path, return changed server-owned progress, prove that the updated server-owned state is ingested, and assert that selection/tab/modal/search/focus/input/scroll remain unchanged.
2. The canonical installer must validate markers that actually exist in the exact generated clean-lineage UI, including the coordination reconciliation mechanism, and must not require `backgroundPulse`.
3. Installer CI must reproduce clean-lineage UI generation and the installer's pre-cutover candidate assertions, not merely parse the shell script.
4. Only after corrected gate 9 and corrected installer qualification pass may another WSL owner handoff be issued.
