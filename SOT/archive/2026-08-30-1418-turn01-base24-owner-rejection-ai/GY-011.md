# GY-011 — Passive AI key fields without operational provider validation and supervisor priming

**Status:** REJECTED  
**Evidence:** Turn 01 Base-24 owner test  
**Decision date:** 2026-08-30

## Rejected approach

Treat AI capability as complete because Configuration contains browser-local Venice/OpenRouter key fields, while omitting the donor's operational model discovery, validation, active provider/model state, and system/supervisor prompt injection.

## Why rejected

A stored key is not an activated inference capability. Without validation and provider/model state, SOT cannot know whether inference is usable. Without a mandatory supervisor/system message, model calls are not grounded in SOT's authority boundaries and can drift into inventing storage facts or treating AI output as execution authority.

## Do not repeat

Do not ship passive credential fields as AI integration. Do not place a supervisor prompt in UI text without proving it reaches every inference request. Do not centralize provider secrets in the database or repository.

## Required replacement

Reuse the operational `devstream-test.html` provider pattern: browser-local keys, model discovery, real validation call, selected provider/model persistence and status. Add an SOT-specific supervisor prompt as the first system message on every inference request, followed by exact project/evidence context and only then the operator request.
