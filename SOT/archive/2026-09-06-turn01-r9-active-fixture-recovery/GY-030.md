# GY-030 — R9 Active-now qualifier required the runtime after creating the synthetic active operation

Date: 2026-09-06
Status: QUALIFICATION FAILURE — PRE-CUTOVER

## Evidence

The owner ran installer commit `c6414e688bc87a7bde3297653044395d5e8918a9`.

The installer passed:
- REQUIRE_TOOLS
- DATABASE_INTEGRITY schema=5
- LIVE_BACKEND
- ARCHIVE_PRECHANGE
- R9_BACKEND_PARSE
- R9_UI_CONTRACT
- R9_DATABASE_BEHAVIOR

The Active-now fixture then failed because the qualifier inserted a fully governed schema-5 running operation and only **afterward** required the backend module. Startup recovery is intentionally unconditional on module/service startup: all queued/running/paused operations are converted to `interrupted` because a service restart cannot assume their worker process survived. Therefore even a correctly linked synthetic operation must become Interrupted when inserted before module startup.

This proves GY-029's proposed fixture correction was incomplete. The product candidate still did not cut over.

## Correct qualification method

Do not weaken startup recovery and do not change the R9 product candidate.

For the Active-now presentation gate:
1. Create a fresh SQLite backup and load the backend module first, allowing startup recovery to complete.
2. Keep that same Node process alive.
3. Insert the synthetic governed WIP operation into the temporary database **after** startup recovery has completed.
4. In that same already-loaded Node process, call `listProjects()` and assert that the running row exposes `WIP`, `40 / 100`, and the matching active operation.

This tests the live-state read path without falsely simulating a service restart.
