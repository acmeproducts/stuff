# GY-044 — Repeated partial-recovery loop: working subsystems without a working product

**Date:** 2026-09-14  
**Status:** REJECTED ARCHITECTURAL / DELIVERY PATTERN

## What failed

Turn 01 and the first Turn 02 reset repeatedly recovered one subsystem at a time, then treated that local success as sufficient foundation for the next release. The result was a succession of mechanically qualified pieces that did not add up to a stable owner-operable application.

Examples from the historical record:

- Windows volume discovery was recovered, while folder access or Source/Target/Backup authority still differed.
- Windows-native browsing became functional, while picker behavior and repeated probing remained poor.
- persistent Node/SQLite processing and bounded workers existed, while the owner-facing lifecycle and state presentation remained contradictory.
- schema-6 SSOT/Profile truth and tag provenance qualified, while the Profile UI was flat and interaction-destructive.
- hierarchy/master-detail qualified, while mobile editing still lost keyboard/focus because polling could replace active DOM.
- a later reset simplified the UI by discarding too much of the persistent engine, producing a thin browser shell instead of a storage system.

The recurring mistake was not lack of effort. It was advancing from a locally repaired layer without first proving the complete operating loop that the owner actually needs.

## Permanent negative rule

Do not release another SOT candidate because a list of internal contracts, static markers, or isolated components pass. A release candidate must prove one complete end-to-end operating slice before adding the next slice.

Do not:

- rebuild the product by chaining old generated HTML or failed candidates;
- use a qualified backend as justification for an unqualified owner workflow;
- use a simplified UI as justification for removing the persistent service architecture;
- allow polling or background reconciliation to reconstruct active interaction DOM;
- split storage authority across Source, Target, Backup, browsing, preflight, or capacity paths;
- present work state that can disagree with durable evidence/revision state;
- advance to planning, protection, deduplication, certification, tags, AI, or other higher layers before storage admission and indexing are proven as an owner-operable loop.

## Required replacement

The recovery design is vertical-slice first:

1. **Foundation:** one persistent Node service, one SQLite database, one authoritative storage catalog, one durable operation/event model, one canonical installer.
2. **Slice A — Storage:** discover real volumes, browse folders, assign Source/Target/Backup, persist and reopen those assignments. No indexing release until this works mechanically and on owner device.
3. **Slice B — Work:** start/re-index, pause/resume/stop, survive browser close/reopen, show durable progress/events, and never destroy active UI state.
4. **Slice C — SSOT Profile:** commit a completed evidence revision atomically and browse the committed virtual volume hierarchically. Failed/stale work cannot replace current truth.
5. **Slice D — Protection/cleanup:** copy/verify/deduplicate/retire/certify only against an explicit committed Profile revision with rollback/audit evidence.
6. Add tags, AI, analytics, or secondary convenience features only after A-D are accepted.

Each slice must have Developer, Manager, Red-team, and owner/device gates. A failed slice returns to its declared clean source; it never becomes an implementation ancestor.

## Historical components that may be reused only as clean source contracts

- Base-20 through Base-22 proved important Windows-native volume discovery/browsing and shared storage-authority behavior, but Base-22 owner testing rejected completed-state rerender and selector ergonomics.
- the later coordination backend proved durable operations/events and bounded worker coordination, but its project-oriented presentation is not the product model.
- R12 proved schema-6 SSOT/Profile and tag-provenance backend behavior, but R12 UI was rejected.
- R13 proved hierarchical master/detail Profile structure, but mobile tag editing remained unstable.
- R14 mechanically qualified but the accumulated owner-facing lineage remained unacceptable and was reset.
- Turn 02 shell reset proved that clearing mutable data is possible, but replacing the service with a browser-owned shell is prohibited.

Reuse means recovering specific clean source contracts and tests, not importing a rejected generated application wholesale.

## Delivery consequence

The next coding turn may start only after the authoritative Turn 02 plan is aligned to this recovery design. The first implementation deliverable after approval is a single canonical WSL installer for **Slice A + the persistent foundation only**. It must not include speculative higher-layer UI or workflow.
